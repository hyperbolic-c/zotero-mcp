核心问题总结

  问题 1：最严重 — ingest_data 逻辑完全重复

  这是该代码库最大的架构问题。AdvancedRAGRetriever.ingest_data() 和
  Ingestor.ingest() 是几乎完全相同的两份实现，约 140 行代码逐字重复。

  重复点对比（advanced_rag.py:110-258 vs ingestor.py:407-548）：
  - 相同的 stats 字典初始化
  - 相同的 md_root 警告逻辑
  - 相同的 force_rebuild 处理（reset collections）
  - 相同的 local DB → API fallback 逻辑
  - 相同的批次累积 + flush 循环
  - 相同的 IndexingProgress 上报

  两者唯一区别：AdvancedRAGRetriever.ingest_data() 用
  self._build_item_chunks()（为了让测试 monkeypatch 生效），而
  Ingestor.ingest() 用 self._build_item_chunks()（同名但是 ingestor
  自己的方法）。这本质是为了满足测试 monkeypatch 需求而引入的架构污染。

  同时，AdvancedRAGRetriever.ingest_data() 混用了两个对象的私有方法：
  # advanced_rag.py:231, 251
  self._flush_batch(...)              # 调用 self
  的方法（AdvancedRAGRetriever）
  self._ingestor._flush_refs_batch(...)  # 直接访问 Ingestor 的私有方法
  这破坏了封装性——facade 直接越过 Ingestor 调用其私有实现。

  ---
  问题 2：_default_parse_creators_string 在两个类中重复定义

  Ingestor._default_parse_creators_string（ingestor.py:78-98）和
  Searcher._default_parse_creators_string（searcher.py:41-61）完全相同，应提取
  为模块级函数或放入 utils.py。

  ---
  问题 3：CHROMA_MAX_BATCH 在两处定义，管理复杂

  # ingestor.py:51
  CHROMA_MAX_BATCH: int = _compute_chroma_max_batch()

  # advanced_rag.py:27
  CHROMA_MAX_BATCH: int = _compute_chroma_max_batch()  # 为了测试 monkeypatch

  设计注释写道"为了测试 monkeypatch
  兼容性"——这是为了补救而引入的重复，不是合理的架构。Ingestor._flush_batch()
  用的是 ingestor.py 的常量（ingestor.py:379），而
  AdvancedRAGRetriever._flush_batch() 则动态 import
  自身模块（advanced_rag.py:341-342）：
  import zotero_mcp.rag.advanced_rag as advanced_rag_module
  MAX_BATCH = advanced_rag_module.CHROMA_MAX_BATCH
  这种运行时自引用 import 是代码味道（code smell），仅为 monkeypatch 而存在。

  ---
  问题 4：Facade 层承担了不该承担的业务逻辑

  Facade 模式的职责是委托，而不是实现。但 AdvancedRAGRetriever 中：
  - ingest_data() 完整实现了 ingest 业务逻辑（应委托给 _ingestor.ingest()）
  - _flush_batch() 重新实现了 flush 逻辑（与 Ingestor 内的实现重复）
  - _build_item_chunks() 委托了但包了一层（为 monkeypatch）
  - __init__ 中额外存储了所有配置的副本（chunk_cfg, retrieve_cfg
  等），这些字段完全冗余

  ---
  问题 5：compat.py 的 monkeypatch 机制设计脆弱

  compat.py 通过 __getattr__ 动态解析属性，让测试能注入替代实现：
  def __getattr__(name: str):
      if name == "is_local_mode":
          # Check if advanced_rag has monkeypatched version

  这种"在运行时检查另一个模块是否被 monkeypatch
  了"的模式极为脆弱，且难以维护。正确的做法是通过依赖注入（构造函数参数）传入这
  些可替换的依赖，而不是通过魔法模块属性查找。

  ---
  问题 6：Ingestor 暴露了过多私有方法给外部

  AdvancedRAGRetriever 直接调用 _ingestor._flush_refs_batch()、_ingestor._fetch
  _items_and_attachments_from_local_db()、_ingestor._collect_attachment_map()——
  所有带下划线前缀的方法。这代表封装层次被打穿，说明 Ingestor
  的公开接口（ingest()）不够完整。

  ---
  问题 7：_hydrate_items 存在 N+1 性能问题

  Searcher._hydrate_items()（searcher.py:127-162）在 local_mode
  下一次性加载所有 items，然后做内存过滤：
  local_items = reader.get_items_with_text(include_fulltext=False)  # 全量加载
  local_by_key = {item.key: item for item in local_items}
  当 Zotero 库有数千个条目时，每次搜索都会全量扫描一次
  SQLite，这是严重的性能问题。应该按 item_keys 列表查询。

  根本原因分析

  这些问题几乎都源于同一个原因：将大类拆分为子模块时，为了维持测试 monkeypatch
  兼容性，在 Facade 层保留了原始实现的副本，导致两套代码长期并存且失去同步。

  正确的重构路径应该是：让 AdvancedRAGRetriever.ingest_data() 直接调用
  self._ingestor.ingest()，测试改为注入 Ingestor 的 mock 对象而非 monkeypatch
  私有方法。
